# 게임 관리

> [메인 지시서](../CLAUDE.md)의 하위 문서. 게임 카드 목록(메인 화면), 실행, 정보 창을 다룬다. 썸네일 저장·드래그앤드롭 공용 인프라는 [공통 관리](common-management.md) 참고.

**관련 파일**: `GameItem.cs`, `GameLibraryRepository.cs`, `MainWindow.xaml`/`.xaml.cs`, `GameInfoWindow.xaml`/`.xaml.cs`, `GameCardSizeSettings.cs`, `GameScreenshotSizeSettings.cs`, `EmptyPathToVisibleConverter.cs`, `SelectExecutableWindow.xaml`/`.xaml.cs`, `RenameFolderWindow.xaml`/`.xaml.cs`, `ProgressColorConverter.cs`, `FileNameHelper.cs`

## 데이터 모델 (`GameItem`)

관리 리스트(`games.json`) 항목 하나. video-vault의 `ManagedVideoItem`과 같은 역할.

| 필드 | 설명 |
|---|---|
| `Id` | 고유 식별자(GUID). 이미지 저장 폴더명 등에 사용 |
| `Name` | 게임 이름. exe 드래그드롭으로 카드를 만들 때 파일명(확장자 제외)으로 자동 채워지며, 정보 창에서 수정 가능 |
| `Version` | 게임 버전 (자유 텍스트) |
| `Description` | 게임 내용 (여러 줄 텍스트) |
| `ExecutablePath` | 실행 파일 경로. 정보 창의 "찾아보기"로 지정/변경 |
| `FolderPath` | (저장하지 않는 계산 값) `ExecutablePath`가 들어 있는 폴더 경로 — 메인 화면 리스트 보기(테이블)의 "폴더" 칼럼에 쓴다. `ExecutablePath`가 바뀔 때마다 다시 계산된다 |
| `ThumbnailPath` | 메인 카드 대표 썸네일. **리사이즈하지 않고 원본 크기 그대로** 저장하고, 화면에는 카드 크기에 맞게 스케일해서 보여준다(아래 "대표 썸네일 지정" 참고) |
| `Screenshots` | 게임 요약 갤러리용 캡처 이미지 경로 목록. `ThumbnailPath`와 마찬가지로 **리사이즈본을 따로 만들지 않고 원본 크기 그대로** 저장하며, 화면에는 갤러리 크기에 맞게 스케일해서 보여준다 |
| `IsCompressed` | 이 게임이 지금 압축(zip)된 상태인지 — 아래 "게임 압축" 참고 |
| `ArchivePath` | 압축 파일 경로 (`AppPaths.GameArchivePath`). 압축 상태가 아니면 `null` |
| `ArchiveSizeBytes` / `CompressedAtUtc` | 압축 파일 크기, 압축을 수행한 시각(UTC). 정보 창의 압축 정보 표시용 |
| `IsBusy` | (저장하지 않는 런타임 전용) 이 게임 자신의 압축/압축 해제가 지금 진행 중인지 — 중복 실행 방지용. 다른 게임의 압축과는 무관 |
| `Rating` / `GentlemanGrade` | 평점 / 신사 등급 (0~100, 실수). 정보 창의 진행바 형태 슬라이더로 표시/편집 — 아래 "정보 창" 참고 |

`ExecutablePath`가 실제로 존재하는지 여부(`IsExecutableValid` 등, JSON에는 저장하지 않는 런타임 계산 값)는 앱 시작 시와 정보 창에서 경로를 바꿀 때마다 `File.Exists`로 다시 판단한다 — 아래 "실행 / 압축 풀기" 절 참고. 압축 파일이 실제로 존재하는지(`IsArchiveValid`)도 같은 시점에 다시 확인한다. 이 둘을 조합한 `IsExecutableMissing`(압축 상태가 아닌데 실행 파일을 찾을 수 없는지)은 메인 화면에서 게임 이름을 빨간 글자로 보여줄지 결정하는 데 쓴다 — 아래 "실행 파일 확인" 참고.

같은 이름의 게임이 버전만 다르게 여러 개 존재할 수 있다(예: 업데이트마다 새 exe로 새 카드를 추가하는 경우). 이를 구분해서 보여주기 위해 `DisplayName`(JSON에는 저장하지 않는 계산 값)을 둔다 — `Version`이 있으면 `"{Name}-{Version}"`, 없으면 `Name`만. 메인 화면 카드 이름과 정보 창 제목 등 게임을 식별해 보여주는 곳은 전부 `Name` 대신 `DisplayName`을 쓴다. 아래 "버전 통합" 절도 이 "같은 이름 = 같은 게임의 다른 버전"이라는 전제를 사용한다.

## 메인 화면 (카드 목록)

- 카드 그리드에 게임 카드를 나열한다. 각 카드: 대표 썸네일 + `DisplayName`("이름-버전", 위 데이터 모델 참고) + 하단 [정보][실행] 버튼 두 개. [실행] 버튼은 압축 상태(`IsCompressed`)면 실행할 파일이 없으므로 비활성화된다 — 압축을 풀려면 카드 우클릭 메뉴의 "압축 풀기"를 쓴다(2026-09-06 버튼에서 메뉴로 이동, 사용자 요청). 아래 "실행 / 압축 풀기" 참고.
- **카드 선택 / F1 / 게임 정보 자동 갱신**: 아이콘 보기(`GamesItemsControl`)는 `ItemsControl`이 아니라 `ListBox`다(2026-09-06 변경, 사용자 요청) — 카드를 클릭하면 선택되고(테두리가 파란색으로 강조됨, `ListBox.ItemContainerStyle`), 리스트 보기(`GamesListView`, 원래부터 `ListView`라 선택 기능이 있었다)와 함께 `MainWindow.GamesSelector_SelectionChanged`가 공용으로 선택된 게임을 `_selectedGame`에 기억한다. **F1**을 누르면 `_selectedGame`의 정보 창을 연다(`MainWindow.MainWindow_PreviewKeyDown`, [정보] 버튼과 같은 `OpenGameInfo` 로직 재사용). 게임 정보 창이 이미 열려 있는 상태에서 다른 게임을 선택하면(F1을 다시 누르지 않아도) 그 창을 닫았다 새로 열지 않고 **그 자리에서 내용만 새 게임으로 바꿔치기**한다(`GameInfoWindow.SwitchTo`) — 텍스트박스/슬라이더/갤러리/압축 정보/창 제목을 전부 다시 채우는 로직(`GameInfoWindow.LoadFromItem`)을 생성자와 공유한다.
  - **선택 위치 기억**: 카드/행을 선택할 때마다 그 게임의 `Id`를 설정(`AppSettings.LastSelectedGameId`)에 즉시 저장한다(2026-09-06 추가, 사용자 요청) — 카드 크기/정렬/보기 방식과 같은 방식으로 선택이 바뀔 때마다 바로 저장하며, 창을 닫을 때까지 기다리지 않는다. 다음 실행 시 `MainWindow.RestoreLastSelectedGame`이 그 `Id`의 게임을 찾아 다시 선택 상태로 만들고 `ScrollGameIntoView`로 화면에 보이게 스크롤한다(정렬/보기 방식이 이미 적용된 뒤에 실행해야 화면 위치가 맞으므로 생성자의 마지막 쪽에서 호출한다). 그 게임이 그 사이 삭제됐으면 조용히 아무 것도 하지 않는다.
- **대표 썸네일 지정**: 이미 만들어진 카드 위에 이미지 파일을 드래그드롭하면 그 카드의 대표 썸네일로 지정된다 ([공통 관리](common-management.md)의 `DragDropImageHelper` 재사용). 게임 요약 스크린샷과 달리 **리사이즈본을 따로 만들지 않고 원본 크기 그대로 저장**한다(`ThumbnailHelper.CopyOriginal`) — 카드 한 장에 한 번만 쓰는 이미지라 미리 축소해둘 이유가 없고, 화면에는 카드 크기(아래 "카드 크기")에 맞게 WPF가 그때그때 스케일해서 보여준다.
  - 카드의 `Border`는 `Background="Transparent"`를 명시적으로 지정한다 — WPF는 `Background`가 `null`인 요소의 빈 공간(자식이 없는 영역, 또는 아직 썸네일이 없어 `Image`가 빈 카드의 내부)을 히트테스트하지 않으므로, 이 설정이 없으면 그 위에 드롭해도 이벤트가 카드가 아니라 그 뒤의 `Window`로 전달되어(그리고 `Window`는 exe가 아닌 파일은 무시하므로) 아무 일도 일어나지 않는 것처럼 보인다(실제로 있었던 버그, 2026-09-05 수정) — 새로 드롭 대상 영역을 추가할 때는 항상 `Background`를 명시한다.
  - **이미 썸네일이 있는 카드에 새 이미지를 드롭해도 화면이 갱신되지 않던 버그**(2026-09-05 수정): `ThumbnailHelper.CopyOriginal`은 항상 같은 경로(`cover.original.{확장자}`)에 저장하므로, 새로 드롭한 이미지의 확장자가 이전과 같으면 `ThumbnailPath`의 문자열 값 자체는 바뀌지 않는다. `GameItem.ThumbnailPath`의 setter는 값이 실제로 달라질 때만 `PropertyChanged`를 올리는 일반적인 최적화라, 이 경우 파일은 새로 덮어써졌는데도 바인딩이 다시 평가되지 않아 카드 이미지가 그대로 남아 있었다. `MainWindow.ApplyThumbnail`이 새 경로를 대입하기 전에 `ThumbnailPath`를 한 번 `null`로 지웠다가 다시 지정해서, 최종 값이 이전과 같은 문자열이어도 항상 변경 알림이 나가도록 고쳤다. 또한 이 참에 새 대표 썸네일을 저장하기 전 기존 `cover.original.*` 파일을 전부 지우도록 해서, 확장자가 바뀌는 경우(예: png → jpg) 옛 파일이 고아로 남는 것도 함께 막았다(`MainWindow.DeleteExistingCoverFiles`).
- **썸네일 삭제**: 카드 우클릭 → 컨텍스트 메뉴 "썸네일 삭제"(대표 썸네일이 있을 때만 나타남 — `GameItem.HasThumbnail`). 게임 카드 자체는 남기고 대표 썸네일 파일만 지운다(파일 삭제 실패해도 목록상의 참조는 지움) — 카드를 통째로 지우지 않고 잘못 지정한 썸네일만 다시 비우고 싶을 때 쓴다. 지금 참조 중인 파일 하나만이 아니라 이미지 폴더의 "cover.original.*" 전부를 지운다(`MainWindow.DeleteExistingCoverFiles` 재사용, 2026-09-06 강화, 사용자 요청) — 새 썸네일로 교체할 때와 같은 정리 로직이라, 확장자가 바뀐 적이 있어 더 이상 참조되지 않는 옛 파일이 남아 있어도 함께 지운다.
- **삭제**: 카드 우클릭 → 컨텍스트 메뉴 "삭제" → 확인 대화상자. `games.json` 목록에서 제거함과 동시에, 이 게임에 연결된 이미지 파일(대표 썸네일, 게임 요약 스크린샷 전부 — [공통 관리](common-management.md)의 `images\{게임 Id}\` 폴더)과, 압축 상태라면 압축 파일(`ArchivePath`)도 함께 삭제한다. 실행 파일(exe)이나 그 폴더(압축되지 않은 상태) 자체는 사용자의 게임 설치 파일이므로 지우지 않는다.
- **카드 크기**: 320x240(기본) / 160x120 두 프리셋을 전역 설정으로 전환한다 (`GameCardSizeSettings`, video-vault의 `IconSizeSettings`와 같은 역할이지만 프리셋이 2개뿐이라는 점이 다르다). **메뉴("보기 > 카드 크기")에서 전환**한다(2026-09-05 툴바에서 메뉴로 이동) — WPF `MenuItem`은 `RadioButton.GroupName`같은 상호 배타 그룹이 없어 `MainWindow.UpdateCardSizeMenuChecks`가 직접 나머지 항목의 체크를 해제한다. 전환하면 화면의 모든 카드가 동시에 바뀐다. 아이콘 보기(아래 "보기 방식")에서만 의미가 있지만, 리스트 보기에서도 메뉴 자체는 계속 보인다(다음에 아이콘 보기로 돌아갔을 때 반영됨).
- **정렬**: 메뉴("보기 > 정렬 > 오름차순/내림차순", 2026-09-06 추가, 사용자 요청)로 게임 목록을 `GameItem.DisplayName` 기준 오름차순(기본)/내림차순으로 정렬한다. `CollectionViewSource.GetDefaultView(_games)`로 얻은 `ICollectionView`(`MainWindow._gamesView`) 하나에 `SortDescription`을 걸어 아이콘 보기/리스트 보기가 공유하므로, 정렬 순서는 항상 두 보기 방식에 똑같이 적용된다 — `games.json`에 저장되는 실제 목록 순서(추가한 순서)는 건드리지 않고 화면에 보여주는 순서만 바뀐다. 카드 크기와 같은 방식으로 `MainWindow.UpdateSortMenuChecks`가 두 메뉴 항목의 상호 배타를 직접 관리하며, 선택한 순서는 설정(`AppSettings.SortOrder`)에 저장되어 다음 실행에도 유지된다.
- **보기 방식**: 메뉴("보기 > 리스트 보기 / 아이콘 보기", 2026-09-06 추가, 사용자 요청)로 두 가지 화면 중 하나를 고른다 — **아이콘 보기**(기본값)는 기존 썸네일 카드 그리드(`GamesItemsControl`)이고, **리스트 보기**는 같은 게임 목록을 테이블(`GamesListView`, `ListView`+`GridView`)로 보여준다. 두 컨트롤 모두 같은 `_gamesView`(위 "정렬" 참고)를 `ItemsSource`로 공유하므로 데이터/정렬은 항상 같고, `MainWindow.ApplyViewMode`가 둘 중 하나의 `Visibility`만 `Visible`로 바꿔 화면에 보이는 모양만 전환한다. 카드 우클릭 메뉴(썸네일 삭제/압축/압축 풀기/삭제)와 이미지 드래그드롭으로 대표 썸네일 지정하는 동작은 `Window.Resources`의 `GameCardContextMenu`와 `Card_DragOver`/`Card_Drop` 핸들러(`ListView.ItemContainerStyle`의 `EventSetter`로 각 행에 건다)를 그대로 공유해서 리스트 보기에서도 동일하게 동작한다 — 다만 리스트 보기 행 자체에는 썸네일 이미지를 표시하지 않는다(2026-09-06 수정, 사용자 요청 — 테이블 형태로 바꾸면서 썸네일 칼럼은 아예 뺐다). 선택한 보기 방식은 설정(`AppSettings.ViewMode`)에 저장되어 다음 실행에도 유지된다.
  - **스크롤**: 아이콘 보기(`GamesItemsControl`, `ListBox`)와 리스트 보기(`GamesListView`, `ListView`) 둘 다 컨트롤 자체 기본 템플릿에 내장된 `ScrollViewer`를 그대로 쓰고, 별도로 감싸는 `ScrollViewer`를 두지 않는다(2026-09-06 수정 — 실제로 겪은 문제: 처음에는 두 보기를 같은 `ScrollViewer` 하나로 함께 감쌌는데, WPF의 `ScrollViewer`는 마우스 휠 이벤트를 처리할 내용이 없어도 일단 자신이 먼저 소비하고 `Handled=true`로 표시해버리는 성질이 있어서, 안쪽의 `ListView`가 자기 `ScrollViewer`에서 휠 이벤트를 항상 먼저 가로채 바깥쪽으로 넘어가지 않았다 — 리스트 보기에서 휠 스크롤이 전혀 안 되는 것처럼 보였다. 두 보기를 감싸는 `ScrollViewer`를 분리해서 해결했다). 이후 아이콘 보기를 `ItemsControl`에서 `ListBox`로 바꾸면서(위 "보기 방식" 참고) `ListBox`가 이미 자체 `ScrollViewer`를 내장한다는 점을 놓치고 예전에 쓰던 감싸는 `ScrollViewer`를 그대로 남겨 둔 적이 있는데, 이렇게 이중으로 감싸면 안쪽(`ListBox` 내장) `ScrollViewer`의 기본 `HorizontalScrollBarVisibility`(`Auto`)가 `WrapPanel`의 가로 폭을 무한대로 측정해버려 카드가 줄바꿈 없이 한 줄로 쭉 나열되는 문제가 있었다(2026-09-07 수정, 사용자 리포트) — 감싸는 `ScrollViewer`를 없애고, `GamesItemsControl`에 `ScrollViewer.HorizontalScrollBarVisibility="Disabled"` / `ScrollViewer.VerticalScrollBarVisibility="Auto"`를 첨부 속성으로 직접 지정해 해결했다.
  - **키보드로 찾기(TextSearch)**: 리스트 보기에 포커스가 있을 때 키보드로 글자를 치면, 윈도우 탐색기처럼 그 글자로 시작하는 `Name`을 가진 행으로 바로 찾아간다(같은/다른 글자를 계속 치면 다음 일치 항목으로 이동, 2026-09-06 추가, 사용자 요청). WPF `ListView`/`ListBox`에 원래 내장된 기능(`TextSearch`)을 그대로 쓴 것으로, 별도 키보드 처리 코드는 없다 — `GamesListView`에 `TextSearch.TextPath="Name"` 한 줄만 지정했다. 커스텀 `GridView` 셀 템플릿을 쓰는 컨트롤은 항목의 기본 텍스트(`ToString`)를 알 수 없어 `TextPath`를 지정하지 않으면 이 기능이 동작하지 않는다.
  - **테이블 칼럼**: 게임 이름(`Name`) / 버전(`Version`) / 평점(`Rating`) / 신사 등급(`GentlemanGrade`) / 폴더(`GameItem.FolderPath` — `ExecutablePath`가 있는 폴더 경로, `ExecutablePath`가 바뀔 때마다 다시 계산되는 계산 값) / 정보(버튼) / 실행(버튼) 순서로 고정이다. **게임 이름/정보/실행은 항상 보이고, 나머지 4개(버전/평점/신사 등급/폴더)는 테이블 헤더를 우클릭하면 나오는 메뉴로 켜고 끌 수 있다**(2026-09-06 추가, 사용자 요청) — `GridView.ColumnHeaderContainerStyle`로 모든 칼럼 헤더에 같은 `ListColumnVisibilityMenu`(체크 가능한 `MenuItem` 4개)를 붙인다. 체크를 바꾸면 `MainWindow.RebuildListColumns`가 `GamesGridView.Columns`를 비우고 "게임 이름 → (켜진 순서대로 버전/평점/신사 등급/폴더) → 정보 → 실행" 고정 순서로 다시 채운다 — `GridViewColumn`은 일반 시각 요소와 달리 한 번 만든 인스턴스를 Columns 컬렉션에 넣었다 뺐다 할 수 있어서 매번 새로 만들 필요가 없다. 어느 칼럼을 켜고 껐는지는 설정(`AppSettings.ListShowVersion`/`ListShowRating`/`ListShowGentlemanGrade`/`ListShowFolder`, 기본값 모두 켜짐)에 저장되어 다음 실행에도 유지된다.
  - 헤더 메뉴의 `MenuItem`들은 `Window.Resources` 안의 `ContextMenu` 리소스에 있어 `x:Name`을 줘도 `InitializeComponent`가 필드를 만들어주지 않는다(리소스 딕셔너리 항목은 페이지 네임스코프 밖) — 그래서 4개 항목마다 별도 `Click` 핸들러(`ToggleVersionColumn_Click` 등)를 두고, 시작 시 초기 체크 상태는 `Resources["ListColumnVisibilityMenu"]`로 리소스를 직접 찾아 `Items` 순서(XAML 선언 순서)로 접근해서 맞춘다.
  - **칼럼 너비 기억**: 헤더 경계를 드래그해서 칼럼 너비를 바꾸면 설정(`AppSettings.ListColumnWidths`, 칼럼 이름 → 너비의 사전)에 저장되어 다음 실행에도 그대로 유지된다(2026-09-06 추가, 사용자 요청). `GridViewColumn.Width`는 보통의 CLR 이벤트가 없는 의존 속성이라, `MainWindow.ApplyListColumnWidths`가 시작할 때 한 번 `DependencyPropertyDescriptor`로 7개 칼럼 전부의 `Width` 변경을 감시하도록 걸어 두고(칼럼을 숨겼다 다시 보여도 같은 칼럼 객체를 재사용하므로 한 번만 걸면 충분하다), 바뀔 때마다 그 칼럼의 이름으로 즉시 저장한다. 표시 여부(위 항목)와 마찬가지로 "게임 이름/정보/실행"을 포함한 7개 칼럼 모두 대상이다.
- **상태바**: 창 아래쪽에 video-vault의 `SeriesManagerWindow`와 같은 형태(아이콘 + 텍스트, 성공/경고/정보/오류 종류별로 색이 다름 — `SetStatus`)로 상태바를 둔다. 게임 추가/삭제/썸네일 지정·삭제/압축 시작·완료/압축 풀기 시작·완료/실행 실패 등 각종 이벤트를 여기 표시한다. 삭제 확인, 압축 확인, exe 여러 개 중 선택처럼 **사용자의 결정이 필요한 경우는 여전히 대화상자**를 쓴다 — 상태바는 결과를 알려주는 용도이지 입력을 받는 용도가 아니다. 시작 시 기본 메시지로 드래그드롭 사용법 안내를 보여준다.

## 게임 목록 파일 관리 (메뉴 "파일")

메인 창 메뉴("파일 > 열기/저장/다른 이름으로 저장")로 게임 목록 파일(`games.json` 형식) 자체를 다룰 수 있다 — 여러 라이브러리를 파일별로 나눠 관리하거나, 백업 파일을 직접 불러오는 등의 용도. `MainWindow._currentGamesPath`가 "지금 이 세션에서 저장/불러오기 대상인 파일"을 기억하며, 기본값은 [공통 관리](common-management.md)의 `AppPaths.GamesPath`(`D:\game\GamePlatform\games.json`)다.

- **열기**: `OpenFileDialog`로 고른 `.json` 파일을 읽어 지금 목록을 통째로 교체한다. 그 파일이 손상돼 있으면(`GameLibraryRepository.Load`의 기존 정책대로) 빈 목록으로 열린다. 연 뒤로는 이 파일이 `_currentGamesPath`가 된다.
- **저장**: `_currentGamesPath`(열기/다른 이름으로 저장으로 마지막에 정해진 파일)에 지금 목록을 즉시 저장한다. 평소에는 게임 추가/삭제 등 모든 변경이 이미 자동 저장되므로, 이 메뉴는 "지금 바로 디스크에 반영됐다는 확인" 용도에 가깝다.
- **다른 이름으로 저장**: `SaveFileDialog`로 새 경로를 골라 저장하고, **그 파일을 새로운 `_currentGamesPath`로 삼는다** — 이후의 모든 자동 저장(카드 추가/삭제, 정보 창 편집, 압축 등)도 이 새 파일을 대상으로 한다(일반적인 텍스트 편집기의 "다른 이름으로 저장"과 같은 동작).
- **백업과의 관계**: [공통 관리](common-management.md)의 자동 일간/주간 백업은 항상 "지금 실제로 저장 중인 파일" 기준으로 동작한다 — `AppPaths.DailyBackupPath`/`WeeklyBackupPath`가 게임 목록 파일 경로를 인자로 받아, 그 파일과 같은 폴더의 `backup\` 하위 폴더에 백업한다. 즉 다른 파일을 열거나 다른 이름으로 저장하면 백업 대상도 자동으로 그 파일로 옮겨간다.
- 이미지(`images\`)/압축 파일(`archives\`) 저장 위치는 게임 목록 파일이 어디에 있든 항상 `AppPaths` 기준(기본 앱 데이터 폴더 밑)으로 고정이다 — 게임 목록 파일만 옮겨 다닐 뿐, 이미지·압축 파일까지 그 위치를 따라가지는 않는다.

## 게임 추가

메인 화면 빈 영역에 아래 세 가지 중 아무 것이나 드래그드롭하면 새 카드가 생긴다 (`MainWindow_Drop`가 확장자/디렉터리 여부로 구분).

- **추가 후 스크롤 이동**: 세 가지 추가 방식 모두 마지막에 `MainWindow.ScrollGameIntoView(item)`을 불러 새로 추가한 카드/행이 있는 위치로 자동 스크롤한다(2026-09-06 추가, 사용자 요청) — 정렬(위 "메인 화면"의 "정렬" 참고)이 걸려 있으면 새 게임이 목록 맨 끝이 아니라 정렬 순서상의 위치에 나타나므로, 지금 보이는 컨트롤(아이콘 보기의 `GamesItemsControl` 또는 리스트 보기의 `GamesListView`, 두 보기 모두 `CollectionViewSource.GetDefaultView(_games)`를 공유하므로 컨테이너 조회 대상만 다르다)에서 `ItemContainerGenerator.ContainerFromItem`으로 새 항목의 컨테이너를 찾아 `FrameworkElement.BringIntoView()`로 스크롤한다. `WrapPanel`/`StackPanel`은 항목을 가상화하지 않으므로 컨테이너는 추가 직후 이미 존재하지만, 레이아웃이 끝난 뒤에 찾도록 `Dispatcher.BeginInvoke(..., DispatcherPriority.ContextIdle)`로 한 박자 늦춘다.
- **이름에서 버전 자동 분리**: exe 파일명/폴더 이름/zip 파일명(확장자 제외)에 `-v1.2.3`/` v1.2.3`/`-1.2.3`처럼 하이픈 또는 공백 뒤에 점으로 나뉜 숫자(2개 이상)가 붙어 있으면, 추가 시점에 `FileNameHelper.SplitNameAndVersion`이 이를 `Name`과 `Version`으로 미리 나눠 담는다(2026-09-06 추가, 사용자 요청) — 예: `"Game-v1.2.3"` → `Name="Game"`, `Version="v1.2.3"`. 폴더 추가는 실제 이동 전 이름(중복 확인용)과 이동 후 최종 폴더 이름 양쪽에 각각 적용한다. 버전처럼 보이는 부분이 없으면 원래 이름 그대로 `Name`에 들어가고 `Version`은 비워둔다.
- **동일한 이름 확인**: 위에서 나눈 `Name`/`Version`을 기준으로 두 단계로 확인한다(`MainWindow.ConfirmAddDuplicateName`, 2026-09-06 추가/수정, 사용자 요청):
  1. **이름과 버전이 모두 같은 게임이 이미 있으면** "이미 있습니다. 그래도 추가할까요?"를 확인 대화상자(예/아니요)로 물어, 완전히 같은 게임을 실수로 중복 추가하는 것을 한 번 막는다.
  2. 그게 아니라 **이름만 같은 게임이 있으면**(대소문자 무시) "버전이 다른 게임인가요?"를 확인 대화상자(예/아니요)로 묻는다 — 위 데이터 모델의 "같은 이름 = 같은 게임의 다른 버전" 전제에 따른 것이다.
  - 두 경우 모두 폴더/압축 파일 이동 등 실제 작업을 시작하기 전에 확인하며, 예를 누르면 추가를 계속 진행하고, 아니요를 누르면 아무 것도 하지 않고(파일 이동/폴더 복사 등도 시작되지 않음) 추가를 취소한다. 같은 이름이 전혀 없으면 바로 진행한다.

- **실행 파일(exe)**: 가장 단순한 경우. `Name`은 파일명(확장자 제외)으로 자동 채워지고, `ExecutablePath`는 드롭한 파일 경로 그대로 — 옮기거나 복사하지 않는다. (exe 하나만 딸랑 드롭하는 경우라 "폴더/압축 파일"을 옮기는 아래 규칙의 대상이 아니다.)
- **폴더**: 그 폴더 안(하위 폴더 포함)에서 `*.exe` 파일을 전부 찾는다. 하나면 바로 그것을 쓰고, 여러 개면 [실행 파일 선택] 대화상자(`SelectExecutableWindow`)를 띄워 사용자가 직접 고르게 한다 — 설치 프로그램/제거 프로그램/재배포 패키지(vcredist 등) 등이 섞여 있을 수 있어 자동 추측은 채택하지 않았다. `Name`은 폴더 이름.
  - **폴더가 이미 [공통 관리](common-management.md)의 `AppPaths.GamesBaseDir`(기본 폴더, 기본값 `D:\game`) 바로 밑에 있으면 그 자리를 그대로 쓴다(`AppPaths.IsDirectlyUnderGamesBaseDir`).** 그 외의 모든 경우 — 다운로드 폴더/다른 드라이브는 물론, **기본 폴더 안에 사용자가 만들어 둔 분류용 하위 폴더(예: `D:\game\- rpg -\게임폴더`)에 있는 경우도 포함** — **등록과 동시에 기본 폴더 바로 밑으로 옮긴다**(2026-09-06 추가, 사용자 요청; 같은 날 "기본 폴더 밑이면 하위 폴더까지 전부 그대로 둔다"는 첫 구현이 분류 폴더 안의 게임을 옮기지 않는 문제로 이어져, "바로 밑"으로 범위를 좁혀 수정 — 실제로 겪은 문제) — `AppPaths.ReserveUniquePath`로 이름이 겹치지 않는 위치를 정한다. **먼저 `Directory.Move`로 옮기는 걸 시도한다(`MainWindow.TryMoveByRename`)** — 대부분의 경우(분류 폴더 → 기본 폴더처럼 같은 드라이브 안에서의 이동)는 실제 데이터를 옮기지 않는 이름 변경 수준이라 폴더 크기와 무관하게 즉시 끝난다. 이게 실패할 때만(다른 드라이브라 `Directory.Move`가 지원하지 않는 경우) 폴더 전체를 파일 단위로 복사한 뒤 원본을 지우는 방식으로 대체한다(2026-09-06 수정 — 실제로 겪은 문제: 항상 복사+삭제 방식만 썼더니 같은 드라이브 안에서 옮길 때도 대용량 게임 폴더가 통째로 복사되어 불필요하게 오래 걸렸다). 복사 대체 경로는 백그라운드 스레드에서 진행하며 상태바에 진행률이 뜬다. 복사가 끝난 뒤 원본 삭제가 실패해도(파일 잠금 등) 게임은 새 위치 기준으로 등록한다 — [게임 압축](#게임-압축)과 같은 "핵심 작업 성공/뒷정리 실패 분리" 원칙.
- **압축 파일(zip)**: **압축을 그 자리에서 풀지 않고, 압축된 상태로 게임을 등록한다** (`IsCompressed = true`). zip 안의 항목을 열어(풀지 않고) `*.exe` 항목을 찾고, 여러 개면 마찬가지로 선택 대화상자를 띄운다. `Name`은 zip 파일명(확장자 제외). 이후 처리:
  1. `AppPaths.GamesBaseDir` 밑에 `{DisplayName}` 폴더를 압축 해제 예정 위치로 예약한다(`AppPaths.ReserveGameFolder` — 실제로 폴더를 만들지는 않는다). `ExecutablePath`는 이 예약된 폴더 밑, zip 안에서 고른 exe의 상대 경로로 미리 계산해둔다.
  2. **압축 파일 자체가 이미 `AppPaths.GamesBaseDir` 바로 밑에 있으면(예: 압축 명령이 만든, 이미 관리 중인 압축 파일을 실수로 다시 추가하려는 경우) 그 자리를 그대로 쓴다(`AppPaths.IsDirectlyUnderGamesBaseDir`).** 그 외의 모든 경우(다운로드 폴더에서 받은 zip, 기본 폴더 안 분류용 하위 폴더에 있는 zip 등) **기본 폴더 바로 밑으로 옮긴다**(2026-09-06 추가/수정, 사용자 요청 — 위 "폴더" 항목과 같은 "바로 밑"만 예외로 인정하는 규칙) — `File.Move`로 옮기며(파일은 드라이브가 달라도 동작한다), 이름이 겹치면 `AppPaths.ReserveUniquePath`가 " (2)" 등을 붙인다. **이 압축 파일은 [게임 압축](#게임-압축) 명령이 만드는 `GamePlatform\archives\` 밑의 내부 관리 위치와는 다르다** — 새로 추가되는 압축 파일은 사용자의 다른 게임들처럼 기본 폴더에 그대로 놓이고, 나중에 이 게임을 압축 해제했다가 다시 압축하는 시점에야 비로소 내부 관리 위치로 들어간다.
  3. 사용자가 나중에 카드 우클릭 메뉴의 "압축 풀기"를 누르면(아래 "실행 / 압축 풀기" 참고) 1번에서 계산해둔 위치에 실제로 풀린다.
  - 압축 해제를 즉시 하지 않는 이유: 이미 압축되어 있는 파일을 굳이 즉시 풀었다가 나중에 또 압축하는 왕복을 피하고, 디스크 공간도 필요할 때까지 아끼기 위함.

## 분류 폴더 안의 게임 정리 (메뉴 "설정")

메인 창 메뉴("설정 > 분류 폴더 안의 게임 정리...")로, **위 "게임 추가"의 "기본 폴더 바로 밑이 아니면 옮긴다" 규칙이 적용되기 전에 이미 등록된 게임**을 한 번에 찾아 정리한다(`MainWindow.CleanUpCategoryFolderGames_Click`, 2026-09-06 추가, 사용자 요청 — 사용자가 `D:\game` 안에 `- rpg -`, `- 2D -` 같은 분류 폴더를 직접 만들어 그 안에서 게임 폴더를 드래그드롭했더니, 분류 폴더까지 포함해서 "이미 기본 폴더 밑"으로 판단되어 옮겨지지 않았던 실제 문제).

- **대상**: 압축 상태가 아닌 게임은 `ExecutablePath`가 기본 폴더 기준 3단계 이상 깊이("분류 폴더/게임 폴더/.../실행 파일")에 있으면 대상이다(`MainWindow.TryGetNestedGameFolder`) — 분류 폴더 바로 밑의 폴더(2번째 세그먼트)를 "게임 폴더"로 보고 통째로 옮긴다. 압축 상태인 게임은 `ArchivePath`가 기본 폴더 바로 밑도 아니고 [게임 압축](#게임-압축)의 내부 관리 위치(`AppPaths.ArchivesDir`, `GamePlatform\archives\` 밑)도 아니면 대상이다(`MainWindow.TryGetNestedArchiveFile`).
- **제외**: exe 파일 하나만 단독으로 등록한 게임(위 "게임 추가"에서부터 옮기는 규칙의 대상이 아니었던 것)은 기본 폴더 밖 어디에 있든 건드리지 않는다. 분류 폴더 바로 밑에 exe가 폴더 없이 단독으로 놓여 있어(2단계 깊이) 같이 옮겨야 할 game 폴더를 특정할 수 없는 경우도 건드리지 않는다.
- 실행하면 먼저 대상 개수를 세어 몇 개를 옮길지 확인 대화상자로 물어본 뒤(예/아니요), 각 게임마다 폴더/압축 파일을 기본 폴더 바로 밑으로 옮기고(이름이 겹치면 `AppPaths.ReserveUniquePath`가 " (2)" 등을 붙인다) `ExecutablePath`/`ArchivePath`를 새 위치로 갱신, 저장한다. 같은 기본 폴더 안에서의 이동은 항상 같은 드라이브이므로 `Directory.Move`로 즉시 옮기며(복사가 아니라 이름 변경 수준이라 폴더 크기와 무관하게 빠르다), 실패하면(파일 잠금 등) 게임 추가와 같은 복사 후 삭제 방식으로 대체한다(`MainWindow.MoveDirectory`).
- 대상이 없으면 안내 메시지만 보여주고 아무 것도 하지 않는다. 이미 진행 중인(`IsBusy`) 게임은 건너뛴다.

## 실행 / 압축 풀기 (Run / Extract)

**[실행]**은 카드의 버튼, **압축 풀기**는 카드 우클릭 메뉴 항목으로 서로 다른 곳에 있다 — 압축 상태(`IsCompressed`)에 따라 둘 중 하나만 의미가 있기 때문이다(`GameItem.IsRunButtonEnabled`/`CanExtract`, 2026-09-06 압축 풀기를 버튼에서 메뉴로 이동, 사용자 요청).

- **[실행] 버튼(카드 하단)**: `Process.Start(ExecutablePath)`로 실행하고, `WorkingDirectory`는 실행 파일이 있는 폴더로 지정한다 (상대 경로로 리소스를 찾는 게임을 위해). 압축 상태이거나 `ExecutablePath`가 비어 있거나 파일이 더 이상 존재하지 않으면 버튼 자체를 비활성화한다 (클릭 시 오류 메시지를 띄우는 대신, 애초에 누를 수 없게 한다).
- **"압축 풀기" 메뉴(카드 우클릭, 압축 상태일 때만 보임 — `GameItem.CanExtract`)**: 압축 파일(`ArchivePath`)을 `ExecutablePath`가 가리키는 폴더 위치(exe로 압축한 게임이면 원래 있던 폴더, zip으로 추가한 게임이면 추가 시 예약해둔 폴더 — 위 "게임 추가" 참고)에 풀고, 압축 파일은 삭제한 뒤 압축 해제 이전 상태(`IsCompressed = false`)로 되돌린다. 압축과 마찬가지로 백그라운드 스레드에서 진행하며 상태바에 진행바가 뜬다 — 아래 "게임 압축" 참고.
- 존재 여부(`IsExecutableValid`/`IsArchiveValid`)는 앱 시작 시 전체 항목에 대해, 그리고 정보 창에서 실행 파일 경로를 바꾸거나 압축/압축 해제를 할 때 다시 확인한다. 이 게임 자신의 압축/압축 해제가 진행 중이면(`IsBusy`) [실행] 버튼과 "압축 풀기" 메뉴 모두 비활성화(또는 숨김)된다.

## 실행 파일 확인

메뉴("설정 > 실행 파일 확인...", 2026-09-06 추가, 사용자 요청)로 등록된 모든 게임의 실행 파일이 실제로 그 자리에 있는지 한 번에 다시 확인한다 — 다른 프로그램으로 게임 폴더를 지우거나 옮긴 경우를 잡아내기 위한 것이다. `MainWindow.CheckExecutables_Click`이 각 게임의 `RefreshExecutableValid()`를 다시 호출할 뿐, 파일을 지우거나 옮기지는 않는다 — 순수하게 상태만 새로 고친다. 확인이 끝나면 상태바에 "실행 파일을 찾을 수 없는 게임이 N개 있어요"처럼 개수를 알려준다.

- **빨간 글자로 표시**: 실행 파일을 찾을 수 없는 게임은 이름이 빨간 글자로 보인다(`GameItem.IsExecutableMissing`, 아이콘 보기의 카드 이름/리스트 보기의 "게임 이름" 칼럼 둘 다 같은 `MainWindow.xaml`의 `GameNameTextStyle` 리소스를 공유해서 처리한다). 압축 상태(`IsCompressed`)인 게임은 원래 실행 파일이 없는 게 정상이므로(위 "게임 압축" 참고) 빨간 글자 대상에서 뺀다 — `IsExecutableMissing`은 `!IsCompressed && !IsExecutableValid`로 정의된다.
- 이 빨간 글자 표시는 메뉴를 눌러야만 나타나는 게 아니라, `IsExecutableValid`/`IsCompressed`가 바뀌는 어떤 시점에도(앱 시작 시, 정보 창에서 실행 파일 경로를 바꿀 때, 압축/압축 해제할 때 등) 항상 최신 상태로 반영된다 — "실행 파일 확인" 메뉴는 그 확인을 지금 당장 전체 게임에 대해 강제로 한 번 더 돌리는 수동 트리거일 뿐이다.

## 게임 이름에서 버전 분리

메뉴("설정 > 게임 이름에서 버전 분리...", 2026-09-06 추가, 사용자 요청)로, `Version`이 비어 있으면서 `Name` 끝에 버전처럼 보이는 부분이 붙어 있는 게임을 한 번에 찾아 `Name`/`Version`으로 나눠 담는다(`MainWindow.SplitNameVersion_Click`) — 위 "게임 추가"의 "이름에서 버전 자동 분리"와 같은 `FileNameHelper.SplitNameAndVersion`을 쓰지만, 이미 등록되어 있는 옛 게임들에도 소급 적용하기 위한 별도 메뉴다.

- **대상**: `Version`이 비어 있고, `Name`이 `FileNameHelper.SplitNameAndVersion` 패턴(하이픈/공백 뒤에 점으로 나뉜 숫자 2개 이상)과 일치하는 게임. 이미 `Version`이 있는 게임은 덮어쓰지 않는다.
- 실행하면 먼저 대상 개수를 세어 몇 개를 나눌지 확인 대화상자로 물어본 뒤(예/아니요), 대상 각각의 `Name`/`Version`을 갱신하고 한 번에 저장한다.
- 대상이 없으면 안내 메시지만 보여주고 아무 것도 하지 않는다.

## 게임 압축

메인 화면 카드 우클릭 → 컨텍스트 메뉴 "압축"(이미 압축된 게임, 또는 이 게임 자신이 지금 압축/압축 풀기 중이면 나타나지 않는다 — `GameItem.CanCompress`).

- `ExecutablePath`가 있는 **폴더 전체**(exe 하나가 아니라 게임을 구성하는 모든 파일)를 확인 대화상자를 거쳐 zip으로 묶어 `AppPaths.GameArchivePath(게임 Id, DisplayName)`(`D:\game\GamePlatform\archives\{게임 Id}\{이름-버전}.zip` — **압축 파일 이름은 메인 화면에 보이는 이름을 그대로 쓴다**, 파일명에 못 쓰는 문자는 `FileNameHelper.Sanitize`가 `_`로 바꾼다)에 저장하고, **원본 폴더는 삭제**해 디스크 공간을 확보한다. `ExecutablePath` 자체(문자열 경로)는 바꾸지 않는다 — 압축을 풀면 같은 위치에 다시 폴더가 생기기 때문이다.
- **백그라운드 스레드에서 진행**한다(`Task.Run`) — 압축 중에도 창을 움직이거나 다른 카드를 조작할 수 있다. 같은 게임을 중복으로 압축/압축 해제하는 것만 `GameItem.IsBusy`로 막으며(그동안 이 카드의 [실행] 버튼과 "압축"/"압축 풀기" 메뉴가 비활성화·숨김된다), **다른 게임은 동시에 압축할 수 있다**.
- **상태바에 진행바를 보여준다**. `System.IO.Compression.ZipFile.CreateFromDirectory`는 진행률 콜백을 제공하지 않으므로, 파일을 하나씩 직접 `ZipArchive.CreateEntryFromFile`로 압축하며 (처리한 파일 수 / 전체 파일 수) 기준으로 퍼센트를 계산해 `IProgress<int>`로 보고한다(`MainWindow.CompressDirectory`). 압축 풀기도 대칭으로 항목 단위 진행률을 보여준다(`MainWindow.ExtractArchive`).
- 실행 파일이 지정되지 않았거나 그 폴더를 찾을 수 없으면 압축하지 않고 안내 메시지만 보여준다.
- 되돌리는 방법은 카드 우클릭 메뉴의 "압축 풀기"(압축 상태일 때만 나타남 — `GameItem.CanExtract`, 위 "실행 / 압축 풀기" 참고)뿐이며, "압축"과 "압축 풀기"는 상태에 따라 둘 중 하나만 보이므로 동시에 나타나지 않는다.
- **압축 자체의 성공/실패와, 그 다음의 원본 폴더 삭제(또는 압축 풀기 후 옛 zip 삭제)의 성공/실패는 서로 다른 단계로 취급한다**(2026-09-05 수정 — 실제로 겪은 버그). zip을 다 만든 뒤에는 게임을 곧바로 "압축됨" 상태로 등록·저장하고, 그 다음에 원본 폴더 삭제를 시도한다 — 삭제가 실패해도 이미 완성된 zip이 `games.json` 어디서도 참조되지 않는 고아 파일로 남지 않는다(상태바에는 "압축은 완료했지만 원본 폴더를 지우지 못했습니다" 경고로 표시됨). 원인이 된 실제 사례: 폴더 안 파일을 백신 실시간 검사/탐색기 등이 잠깐 잠가서 `Directory.Delete`가 "다른 프로세스가 사용 중"으로 실패했는데, 그때는 압축 자체까지 통째로 실패로 표시되면서 완성된 zip이 등록되지 않고 남아 있었다.
- **같은 잠금 오류가 또 나도 문제가 남지 않도록 두 겹으로 대응한다**(2026-09-05 추가):
  1. 그 자리에서 바로: `MainWindow.RetryDelete`가 실패 시 1초 간격으로 최대 10번(총 약 9초) 재시도한다.
  2. 그래도 안 풀렸으면: 압축된 상태(`IsCompressed = true`)인데 원본 폴더가 아직 남아 있는 게임을 앱 시작 시마다 `CleanUpLeftoverCompressedFoldersAsync`가 조용히 다시 지워본다(3번, 1초 간격) — 대부분의 파일 잠금은 몇 초~몇 분 안에 풀리므로, 다음 실행 시점에는 대개 성공한다. 이번에도 실패하면 아무 메시지 없이 넘어가고 그 다음 실행 때 다시 시도한다 — 게임 데이터(zip)는 이미 안전하게 등록되어 있으니 디스크 공간이 조금 늦게 회수될 뿐, 사용자가 뭔가 조치할 필요는 없다.

## 정보 창 (`GameInfoWindow`)

카드의 [정보] 버튼을 누르면 열리는 창. 표시/편집 항목:

- **게임 이름**, **게임 버전** — 한 줄 텍스트박스
- **게임 내용** — 여러 줄 텍스트박스 (`Description`)
- **실행 파일 경로** — 텍스트박스 + "찾아보기"(`OpenFileDialog`) 버튼으로 `ExecutablePath` 지정/변경
- **게임 폴더 이름 변경...** 버튼(`RenameGameFolder_Click`, 2026-09-06 추가, 사용자 요청) — 실행 파일이 들어 있는 폴더(`Path.GetDirectoryName(ExecutablePath)`) 자체의 이름을 바꾼다. 작은 입력 대화상자(`RenameFolderWindow`, `SelectExecutableWindow`와 같은 패턴)에 현재 폴더 이름이 미리 채워져 있고, 새 이름을 입력하고 확인하면 `Directory.Move`로 폴더 이름을 바꾼 뒤 `ExecutablePath`를 새 위치 기준으로 갱신한다(실행 파일이 폴더 바로 밑이 아니라 그 밑 하위 폴더에 있어도 상대 경로를 유지한다). 새 이름은 `FileNameHelper.Sanitize`로 파일명에 못 쓰는 문자를 정리하고, 대소문자만 바꾸는 경우(윈도우는 대소문자를 구분하지 않으므로 `Directory.Move`가 같은 경로로 인식해 아무 일도 하지 않는다)는 임시 이름을 한 번 거쳐 우회한다. 압축 상태라 폴더가 실제로 존재하지 않거나(위 "게임 압축" 참고), 같은 이름의 폴더/파일이 이미 있으면 안내만 하고 아무 것도 하지 않는다. **게임 이름(`Name`)과는 무관한 별개의 동작**이다 — 폴더 이름만 바뀌고 카드에 표시되는 `DisplayName`은 그대로다.
- **압축 정보** — 압축 상태(`IsCompressed`)일 때만 보이는 패널. 압축 파일 경로/크기/압축 일시를 보여준다 (편집 불가, 표시 전용). 메인 화면에서 압축/압축 해제를 하면 이 창이 열려 있어도 즉시 갱신된다.
- **평점 / 신사 등급** — 게임 요약 바로 위에 나란히(2열) 배치된 두 항목(`GameItem.Rating`/`GentlemanGrade`, 0~100, 2026-09-06 추가, 사용자 요청). 압축 진행바와는 무관한 별개의 UI다. 각 항목은 "슬라이더 + `<`/`>` 버튼 + 텍스트박스" 한 줄로 구성된다(2026-09-06 추가, 사용자 요청) — 슬라이더의 어느 지점이든 클릭/드래그해도(`IsMoveToPointEnabled="True"`), `<`/`>`로 1씩 증감해도, 텍스트박스에 직접 숫자를 입력해도 셋 다 항상 같은 값으로 맞춰진다(`GameInfoWindow.SetRating`/`SetGentlemanGrade`가 한 곳에서 모으고, `_isSyncingRating`/`_isSyncingGentlemanGrade`로 서로 값을 되돌려 쓰다가 무한 루프에 빠지는 것을 막는다). 슬라이더는 sample.png 참고 디자인처럼 값 구간(0-20/20-40/40-60/60-80/80-100)마다 **채워진 막대** 색이 청록→하늘색→보라→분홍→주황으로 바뀌는 알약 모양이고, 안 채워진 배경은 연한 회색(`#E3E3E3`)으로 고정이다(`ProgressColorConverter`가 값→그라데이션 브러시 변환, `GameInfoWindow.xaml`의 `RatingSliderStyle`; 2026-09-06 수정 — 처음에는 배경이 색이고 채운 막대가 흰색이었는데, 사용자 요청으로 서로 바꿨다. 퍼센트를 막대 위에 흰 글씨로 겹쳐 쓰면 흰 채움 위에서 안 보이는 문제가 있어, 값은 옆 텍스트박스에만 표시한다). 값이 바뀌면 다른 필드와 마찬가지로 즉시 저장된다.
- **게임 요약** — 캡처 이미지 갤러리. **첫 번째 슬롯은 항상 메인 화면 대표 썸네일(`ThumbnailPath`)이다** — 실제 `Screenshots` 목록의 항목이 아니라 표시 전용으로 맨 앞에 얹는 것이며("대표 이미지" 라벨 표시), 여기서 삭제할 수 없다(대표 썸네일을 바꾸려면 메인 화면 카드에 새 이미지를 드래그드롭한다). 대표 썸네일이 아직 없으면 이 슬롯은 빈 이미지 placeholder("썸네일 없음")로 보여준다. 두 번째 슬롯부터가 실제 `Screenshots`이며, 창 안에 이미지 파일을 드래그드롭하면 뒤에 추가된다. 개별 삭제는 항목 우클릭으로 처리하며, 목록에서 빼는 동시에 이미지 파일(`images\{게임 Id}\`)도 함께 지운다(`GameInfoWindow.DeleteScreenshotFiles`) — 대표 썸네일 슬롯은 삭제 메뉴 자체가 나타나지 않는다. **항목을 클릭하면 원본 이미지를 크게 보여주는 뷰어가 열린다** (video-vault의 `OriginalImageWindow`와 동일한 방식 — 아무 곳이나 클릭하면 닫힘; 대표 썸네일 슬롯이 비어 있을 때 클릭하면 아무 반응도 하지 않는다). 메인 화면에서 대표 썸네일을 바꾸면 이 창이 열려 있어도 첫 슬롯이 즉시 따라간다.
- **게임 요약 이미지 크기**: 320x240(기본) / 160x120 / 80x60 세 프리셋을 전역 설정으로 전환한다 (`GameScreenshotSizeSettings`, 메인 화면의 `GameCardSizeSettings`와 같은 패턴이지만 프리셋이 3개이고 카드 크기와는 별개로 관리된다 — 두 설정을 동시에 같은 값으로 맞출 필요는 없다). 전환하면 열려 있는 갤러리의 모든 이미지가 동시에 바뀐다.
- **버전 통합**: "이름이 같은 모든 버전에 게임 내용/게임 요약 통합" 버튼을 누르면, `Name`이 같은 다른 `GameItem`(다른 버전)을 모두 찾아 게임 내용과 게임 요약을 하나로 합친 뒤 그 결과를 **모든 버전에 동일하게** 반영한다 — 단순히 지금 열린 항목에 다른 버전 내용을 가져오는 것이 아니라, 이후 어느 버전의 정보 창을 열어도 같은 내용/요약을 보게 만드는 동작이다.
  - **게임 내용**: 각 버전의 `Description`을 `"[버전]\n내용"` 형식으로 순서대로 이어붙인다(빈 설명은 제외).
  - **게임 요약**: 모든 버전의 스크린샷(원본 크기 파일 하나씩)을 모아, 각 버전의 이미지 폴더(`images\{게임 Id}\`)에 복사해 넣는다 — 버전마다 자기 폴더에 사본을 독립적으로 갖게 되므로, 한 버전을 삭제해도 다른 버전의 스크린샷은 영향받지 않는다(위 "삭제"의 폴더별 소유권 규칙과 일관됨).
  - **대표 썸네일**: 게임 내용/게임 요약과 달리, 대표 썸네일이 **아직 없는 버전에만** 다른 버전의 대표 썸네일을 가져와 채운다(`GameInfoWindow.ApplyThumbnailFrom`, 2026-09-06 추가, 사용자 요청) — 이미 자기 대표 썸네일이 있는 버전은 그대로 둔다(의도적으로 버전별 다른 표지를 쓰고 있을 수 있어서, 게임 내용처럼 전부 덮어쓰지 않는다). 가져올 원본은 이 정보 창을 연 버전 자신의 대표 썸네일을 우선 쓰고, 그것도 없으면 다른 버전 중 대표 썸네일이 있는 첫 번째 것을 쓴다. 어느 버전에도 대표 썸네일이 없으면 아무 것도 하지 않는다. 메인 화면 카드에 이미지를 직접 드래그드롭할 때(`MainWindow.ApplyThumbnail`)와 같은 방식으로 각 버전 자신의 이미지 폴더에 사본을 복사해 넣는다(원본 파일은 지우지 않음).
  - 같은 이름의 다른 버전이 없으면(즉 이 게임 하나뿐이면) 안내 메시지만 보여주고 아무 것도 하지 않는다.
  - 한 번 통합한 뒤에 어느 한 버전의 내용을 다시 고치면 다른 버전과 달라질 수 있다(자동으로 계속 동기화되지 않음) — 필요하면 버튼을 다시 눌러 재통합한다.
- **창은 한 번에 하나만 연다**: 이미 `GameInfoWindow`가 열려 있는 상태에서 다른 카드의 [정보]를 누르면, 열려 있던 창을 닫고 새 게임 정보로 새 창을 연다 (video-vault의 `SingleInstanceWindow<T>` 패턴을 그대로 사용 — [공통 관리](common-management.md) 참고). 게임별로 별개 창을 유지하지 않는다. 다만 메인 화면에서 카드를 클릭/선택만 해도(F1이나 [정보] 버튼을 다시 누르지 않아도) 열려 있는 이 창이 새로 선택한 게임으로 바로 갱신된다 — 위 "메인 화면"의 "카드 선택 / F1 / 게임 정보 자동 갱신" 참고. 이 경우는 창을 닫았다 새로 여는 게 아니라 `GameInfoWindow.SwitchTo`로 같은 창 인스턴스의 내용만 바꾸는 것이다.
- **저장 시점**: 별도의 "저장" 버튼 없이, 이름/버전/설명/실행 파일 경로/게임 요약/이미지 크기 설정 등 무엇이 바뀌든 즉시 `games.json`(과 설정 변경 시 `settings.json`)에 자동 저장한다. 창을 닫을 때 "저장하지 않은 변경사항" 확인 절차는 없다(이미 저장되어 있으므로).
- **창 위치/크기 기억**: 이 창도 [공통 관리](common-management.md)의 "창 위치/크기 기억" 규칙을 따른다 — 닫을 때의 위치/크기를 기억했다가 다음에 열 때 그대로 복원한다.
